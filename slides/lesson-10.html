Part one

Where results live

Why a row store cannot be indexed out of this problem, and what a database has to do differently to answer analytical queries in milliseconds.

the tension

Fast queries want precomputed answers; fresh data wants raw events. You cannot fully have both.

Fast query

Pre-compute the answer before the question arrives.

  • Microseconds to single-digit milliseconds.
  • You must anticipate every question.
  • Every materialized view is another thing that can break or drift.

Fresh data

Keep raw events and compute at query time.

  • Ask any question, adapt to new dashboards.
  • You need an engine fast enough to scan millions of rows in milliseconds.
  • The faster the raw scan, the less pre-aggregation you need.
ⓘ
In the wild: a leaderboard cache, an hourly sales dashboard, a "top products this week" widget — all pre-computed, all wrong the instant something changes underneath them.
ⓘ
In the wild: a fraud investigator's ad-hoc query, a "why did revenue spike at 2pm" drill-down — questions nobody anticipated, answered from raw events.
read amplification

Just add an index?

In Lesson 1 a B-tree index made a Postgres lookup fast. Try the same instinct on an analytical scan.

  • A 100M-row orders table, 12 columns, ~200 bytes/row on disk → ~20 GB total.
  • Your query needs 2 of those 12 columns — event_type and amount — about ~3.3 GB of actual data.
  • A row store's unit of I/O is the row. To read any column, Postgres pulls the whole row off its page — all 20 GB, not 3.3.
!
6× read amplification — before a single byte of the answer is computed. An index on event_type does not fix it: past roughly 5-10% selectivity the planner abandons the index and scans anyway, and even an index-only scan only ever covers the columns you happened to index.
✓
The problem is not indexing effort. It is physical layout: row-major storage puts every column of a row on the same page, so touching one column costs you all of them.
storage

One file per column

MergeTree writes a separate, sorted file per column inside every part. A query opens only the files it names.

Layout

  • A 2-of-12-column query → ClickHouse opens 2 files, not 12.
  • Each part is immutable: column files plus a sparse index (next slide).

Why it compresses

  • Sorted by event_type first → thousands of identical values in a row → runs compress to almost nothing.
  • event_time is monotonic within a run → delta encoding stores small diffs, not full 8-byte timestamps.
  • amount is high-entropy decimals → little pattern to exploit.
ⓘ
Compression ratio is a property of the data's shape, not the codec. Sorting is what creates that shape.
predict · compression

Guess the compression ratio

Same table, three columns, very different shapes: region (a handful of values), event_time (a timestamp), amount (high entropy). Predict the ratio for each before you look.

ClickHouse · system.parts_columns
SELECT column, formatReadableSize(sum(column_data_compressed_bytes)) AS compressed, formatReadableSize(sum(column_data_uncompressed_bytes)) AS uncompressed, round(sum(column_data_uncompressed_bytes) / sum(column_data_compressed_bytes), 1) AS ratio FROM system.parts_columns WHERE table = 'events' AND active GROUP BY column ORDER BY ratio DESC;

tradeoff

Pre-aggregation or on-the-fly?

Pre-aggregation

Materialized views, rollup tables, OLAP cubes.

  • Latency: microseconds.
  • Question must be known in advance.
  • Operational tax: sync, drift, stale data.

On-the-fly

Raw or lightly transformed events.

  • Latency: depends on scan speed.
  • Ask anything, drill down ad-hoc.
  • Needs a fast columnar engine.
✓
Key insight: the faster your OLAP engine is at raw scans, the less pre-aggregation you need — and the simpler your system becomes.

the callback

MergeTree is an LSM tree

  • Writes are append-only: no random I/O, no rewriting existing rows.
  • A CDC stream carries updates and deletes (Lesson 5); MergeTree is append-only — ReplacingMergeTree is how the merge resolves that tension.
  • Tradeoff: write amplification. A row may be rewritten 3-5 times before it reaches its final merged state.
ⓘ
You already met this shape in Lesson 8: RocksDB held Spark/Flink's windowed state as an LSM tree, same append-then-compact structure. Different job — RocksDB durabilizes streaming state; MergeTree serves the query.
the sparse index

ClickHouse does not index every row

One mark per granule — 8192 rows by default. For 100M rows that's ~12,200 marks; for a billion, ~122,000. Small enough to sit in memory.

  • The filter matches the (event_type, region, event_time) ORDER BY prefix → matching rows are contiguous → one bounded range of granules.
  • Filter on a column not in that prefix (say, user_id) → matches scatter across every granule → the engine reads them all.
✓
This is the mechanism Part two's ORDER BY experiment measures directly: same data, two sort orders, an order-of-magnitude difference in granules scanned.
schema

The source table

MergeTree stores immutable parts, sorted by the ORDER BY key. That key is the primary index.

ClickHouse
-- raw event store CREATE TABLE IF NOT EXISTS events ( event_time DateTime64(3), user_id UInt32, event_type LowCardinality(String), amount Decimal(10, 2), region LowCardinality(String) ) ENGINE = MergeTree() PARTITION BY toYYYYMMDD(event_time) ORDER BY (event_type, region, event_time) SETTINGS index_granularity = 8192;
ⓘ
LowCardinality(String) is explicit dictionary encoding for columns with few distinct values. DuckDB does this automatically; ClickHouse makes you declare it.
the fourth log

The Kafka engine table

events_kafka is a consumer, not a query target. Selecting from it consumes messages from the topic.

ClickHouse
CREATE TABLE IF NOT EXISTS events_kafka ( event_time String, user_id UInt32, event_type String, amount Decimal(10, 2), region String ) ENGINE = Kafka() SETTINGS kafka_broker_list = 'kafka:9092', kafka_topic_list = 'events', kafka_group_name = 'clickhouse-consumer-l10', kafka_format = 'JSONEachRow', kafka_max_block_size = 1000, kafka_poll_timeout_ms = 100, kafka_flush_interval_ms = 1000, kafka_auto_offset_reset = 'earliest'; CREATE MATERIALIZED VIEW IF NOT EXISTS events_kafka_mv TO events AS SELECT parseDateTime64BestEffort(event_time) AS event_time, user_id, event_type, amount, region FROM events_kafka;
!
This is a Kafka consumer group. kafka_group_name = 'clickhouse-consumer-l10' commits offsets like any other consumer — your fourth log, after the Postgres WAL, the replication slot, and the Kafka topic itself. Delivery is at-least-once: a crash between poll and flush can replay a block. Part two tunes kafka_max_block_size, kafka_poll_timeout_ms, kafka_flush_interval_ms — together they set the floor on ingestion latency. (auto.offset.reset is a librdkafka property, not a table setting: it lives in config/clickhouse-kafka.xml.)

trigger on insert

A materialized view is a trigger

When data arrives in events, the MV runs on the new block and writes partial aggregates to revenue_by_region_minute.

sql/init_clickhouse.sql
CREATE TABLE revenue_by_region_minute ( minute DateTime, region LowCardinality(String), total_revenue AggregateFunction(sum, Decimal(10, 2)), purchase_count AggregateFunction(count), unique_users AggregateFunction(uniq, UInt32) ) ENGINE = AggregatingMergeTree() ORDER BY (region, minute); CREATE MATERIALIZED VIEW revenue_by_region_minute_mv TO revenue_by_region_minute AS SELECT toStartOfMinute(event_time) AS minute, region, sumState(amount) AS total_revenue, countState() AS purchase_count, uniqState(user_id) AS unique_users FROM events WHERE event_type = 'purchase' GROUP BY minute, region;
!
Gotcha: those -State columns don't hold numbers. Next slide.
gotcha

A partial aggregation state is not a number

total_revenue is typed AggregateFunction(sum, Decimal(10,2)). Read it raw and you get an unreadable binary state, not a revenue figure.

  • Write: sumState / countState / uniqState — one partial state per insert block, per key.
  • Read: sumMerge / countMerge / uniqMerge — combine whatever states matched. This is what /api/revenue calls, every time.
  • Not FINAL: FINAL forces a synchronous merge of every matching part before it answers — the background work you pre-aggregated to avoid, now on your query's clock, worst exactly when parts are piling up fastest. It doesn't even decode the state — you'd still need -Merge afterward.
src/app.py · GET /api/revenue
SELECT minute, region, sumMerge(total_revenue) AS revenue, countMerge(purchase_count) AS purchases, uniqMerge(unique_users) AS unique_users FROM revenue_by_region_minute WHERE minute >= now() - INTERVAL {minutes:UInt16} MINUTE GROUP BY minute, region ORDER BY minute DESC, region

the core tradeoff

Ingestion latency vs. query latency

freshness

How long after an event occurs before it is queryable?

  • Controlled by kafka_max_block_size
  • Smaller blocks = lower latency
  • But more parts to scan

query speed

How long does a query take to return?

  • More parts = more index lookups
  • Controlled by merge aggressiveness
  • Merge work competes with queries for CPU/I/O
✓
The right knob depends on the dashboard SLA. 5-second refresh? 2-3s ingestion latency is fine. Fraud alert? Push smaller batches and accept more query overhead.

Which knob is the floor?

src/demo_ingest_floor.py sweeps two settings, one canary each, timed until ClickHouse can see it. Act 1 moves kafka_max_block_size over a 1000× range; act 2 moves kafka_flush_interval_ms. Predict which one moves the number.

which knob is the floor?
ACT 1 · block size, flush fixed at 1000ms kafka_max_block_size = 65536: 1.49s kafka_max_block_size = 64: 1.51s <-- flat across 1000x ACT 2 · flush interval, block size fixed at 1000 kafka_flush_interval_ms = 2000: 1.65s kafka_flush_interval_ms = 1000: 1.51s kafka_flush_interval_ms = 500: 1.03s kafka_flush_interval_ms = 100: 0.11s <-- there it is
!
One canary never fills a block of any size — so the block size cannot be what ends the batch. The flush timer is. Block size only binds once the stream is fast enough to fill a block before the timer fires, and a 1000/s producer is not fast enough: a 1000-row block takes ~1s to fill, the same as the timer, so the two tie and freshness stays around 1.0s. At 20 000/s the block fills in ~50ms and p50 drops to 0.14s. Which knob matters depends on your arrival rate.

diagnose

When query latency degrades, look here

Two system tables answer the question directly: are merges keeping up with inserts?

ClickHouse
-- how many active (unmerged) parts per table? SELECT table, count() AS active_parts, sum(rows) AS total_rows FROM system.parts WHERE active AND table IN ('events', 'revenue_by_region_minute') GROUP BY table; -- what's merging right now, and how far along? SELECT table, elapsed, progress, num_parts FROM system.merges;
!
active_parts climbing over time means the merge scheduler is falling behind the insert rate — every query now opens more files and does more index lookups. Merges are background CPU and I/O work; under a full-rate producer they compete directly with your dashboard queries for the same machine.

Part three

The hard parts.

Everything so far assumed inserts only arrive once and never change. Duplicates, updates, and deletes say otherwise — and then we ask whether any of the last four lessons were necessary at all.

gotcha

At-least-once means at least.

The Kafka table engine is a consumer group. Every consumer group in this course has been at-least-once. This is where that guarantee lands on your revenue number.

!
The failure: ClickHouse commits a Kafka block's offset only after the insert into events succeeds. Restart between those two steps — OOM, deploy, a dropped connection — and on reconnect it re-reads the same block. events has no primary key to reject it: row count goes up by one full block (kafka_max_block_size rows), sum(amount) goes up by whatever that block summed to. No error. No warning.
  • insert_deduplication_token — tag each insert with a token derived from the Kafka partition + offset range; a replayed block gets the same token and ClickHouse drops it. Requires non_replicated_deduplication_window > 0 — off by default on plain MergeTree, and only works if you control the insert path yourself.
  • ReplacingMergeTree — stop trying to prevent the duplicate and make the table indifferent to it instead. The structural answer, next slide.

closing the loop · lesson 5

Where do U and D go?

Lesson 5's CDC stream emitted "action": "I" / "U" / "D", applied to DuckDB with idempotent DELETE + INSERT. MergeTree has no per-row DELETE or UPDATE in that path. Every action becomes an INSERT.

ClickHouse
CREATE TABLE orders ( id UInt64, status LowCardinality(String), updated_at DateTime64(3), _version UInt64, is_deleted UInt8 ) ENGINE = ReplacingMergeTree(_version, is_deleted) ORDER BY id; -- I and U: INSERT, is_deleted = 0, _version = event epoch ms -- D: INSERT, is_deleted = 1, same row otherwise unchanged
!
Dedup happens at merge time, and merges run on ClickHouse's own schedule — not yours. A query between two merges can see one version, the other, or both. Use FINAL or an aggregation that tolerates duplicates. Never trust a raw SELECT on a ReplacingMergeTree.

tradeoff

What FINAL costs.

SELECT ... FROM orders FINAL forces ClickHouse to merge every part touching your key range, in memory, before it answers. Correct, but not free.

ApproachCorrectnessCost
FINALAlways correctMerge-on-read, scales with unmerged parts
GROUP BY + argMaxAlways correctOne scan, no merge triggered — every query pays it
Raw SELECT, no dedupCorrect only after the next mergeCheapest — reads exactly what's on disk
the argMax pattern
SELECT id, argMax(status, _version) AS status FROM orders GROUP BY id HAVING argMax(is_deleted, _version) = 0;
✓
The same shape as every tradeoff this course has measured: Spark's trigger interval, Flink's watermark bound, and now FINAL. Correctness and latency trade against each other. You choose by SLA — you don't get the default for free.
correction

The escape hatches that do exist.

Two hours ago: pick ORDER BY once, no later fix. Still true for the base table. But two tools add a secondary access path without rewriting it.

Skip indices

  • minmax — per-granule min/max, prunes numeric ranges
  • set(N) — per-granule distinct values, prunes equality
  • bloom_filter — probabilistic membership, high cardinality

ALTER TABLE events ADD INDEX idx_amount amount TYPE minmax GRANULARITY 4;

Projections

  • A second sort order, stored and kept in sync for you
  • ClickHouse picks base table or projection per query
  • This is events_by_user_demo from two slides ago, automated

ALTER TABLE events ADD PROJECTION by_user (SELECT * ORDER BY user_id);

!
What neither does: change the base table's physical layout, or turn a wrong ORDER BY into a right one for your dominant query. A projection is a full second copy of the data — it costs storage, and every insert now writes it twice.

housekeeping

A table with no TTL fills the disk.

Kafka retains by time and rolls old segments off automatically. events does not, unless you tell it to.

ClickHouse
ALTER TABLE events MODIFY TTL event_time + INTERVAL 7 DAY TO VOLUME 'cold', event_time + INTERVAL 30 DAY DELETE;
ⓘ
TTL is enforced during background merges, the same schedule that compacts parts — it is lazy, not instant. Tiered storage needs a second volume configured in advance; this moves parts to it, then drops them, with no second table to maintain.
landscape

Did I need Flink?

The revenue_by_region_minute_mv you built earlier today triggers on every insert and maintains incremental aggregate state. That is stream processing. So what did Lessons 7-9 buy you?

CapabilityClickHouse MVSpark / Flink
Triggers onOne insert blockMicro-batch trigger or continuous operator
Watermarks, late dataNoneConfigurable lateness, drop or hold
Stateful joins with TTLNoneKeyed state, TTL-managed
Per-key state machinesSQL onlyArbitrary code (ProcessFunction, mapGroupsWithState)
Exactly-once, external sinksBest-effortCheckpointed, transactional
✓
Reach for an MV when the aggregation is a rollup over data already landing in the table. Reach for a stream processor when correctness depends on event time — lateness, ordering, or state that outlives one insert block.

capstone

The latency budget.

One fact, every hop it travels from commit to pixel. Ten lessons, one number each.

① Postgres commit L1 ____ ← fill from your L1 run (load_async.py) ② WAL → replication slot (logical decode) L5 ____ ← fill from your L5 run (watch_lag.py) ③ CDC event → Kafka topic L6 ____ ← fill from your L6 run (watch_lag.py) ↪ optional detour: Kafka → Spark/Flink job L7-9 ____ ← fill from your L9 run (analyze_latency.py) ④ Kafka → ClickHouse Kafka engine → MergeTree part L10 0.05s (p95 1.06s — measure_freshness.py) ⑤ materialized view updates, same insert block L10 no extra hop — the MV rides the flush ⑥ dashboard query returns L10 7.3 ms (p99 63.5 ms — query_loadtest.py) ⑦ browser paint — not in this course
✓
End-to-end latency is the sum of every hop above, and you've now measured every term you can reach. “Real-time” was never a property you bought — it's a budget you allocate, term by term.
honesty

What these numbers don't prove.

  • One machine: ClickHouse, Kafka, and the producer share a laptop's CPU and disk — no network hop between them.
  • One node: no replication, no failover. ReplicatedMergeTree and its coordination story went untested.
  • Synthetic, uniform load: a steady producer rate, no traffic bursts, no skewed keys, no dead partitions.
  • Warm cache, one concurrency level: queries hit data already in page cache; ten clients is not peak traffic.
  • Tiny by ClickHouse standards: thousands to low millions of rows. Skip indices and projections earn their keep at billions.
✓
The mechanism holds: at-least-once, merge-time dedup, ORDER BY as primary index, FINAL's cost. The exact milliseconds will move, by a lot, at production scale and concurrency.

Ten lessons, one row.

A row in Postgres became a WAL record, became a CDC event, became a Kafka message, became windowed state, became a measured latency distribution, became a column in an OLAP engine, became a number on a dashboard.

Every one of those transformations costs money, latency, and operational burden. Nothing in this course was free, and nothing was mandatory. The skill was never the tools. It was measuring whether you needed them.
