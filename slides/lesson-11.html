predict · the crash

Spark writes a batch, then dies.

It writes a batch to ClickHouse, then dies before checkpointing. What happens?

✓
The batch is replayed. Spark restarts from the last checkpoint, which never advanced, and re-reads the same Kafka offsets. ClickHouse physically gains duplicate rows — the same order_id and the same LSN, written twice. The API answer does not change — the duplicate rows share a version, so a collapse at read time treats them as one.
what today proves

Atomicity ends at the system boundary.

Postgres commits. Kafka commits. Spark checkpoints. ClickHouse merges. None of those four commits is the same commit.

so what IS true

Effectively-once current state.

lesson11.orders_current
CREATE TABLE lesson11.orders_current ( order_id UInt64, customer_id UInt32, amount Decimal(10, 2), status LowCardinality(String), -- L10: 213.5x compression created_at DateTime64(3, 'UTC'), updated_at DateTime64(3, 'UTC'), version UInt64, -- Debezium source.lsn _is_deleted UInt8, source_topic LowCardinality(String), -- event identity, L6 kafka_partition UInt16, kafka_offset UInt64, source_ts DateTime64(3, 'UTC'), ingested_at DateTime64(3, 'UTC') DEFAULT now64(3) ) ENGINE = ReplacingMergeTree(version) PARTITION BY modulo(order_id, 16) ORDER BY order_id;
ⓘ
FINAL collapses every version at query time; the highest version wins. A delete is not a physical delete — it's a row with a higher LSN and _is_deleted=1 that wins the same collapse.
!
This is not a distributed transaction. No two-phase commit spans Postgres, Kafka, Spark and ClickHouse. It is convergence: given enough time, every reader sees the same current state.

schema contracts, drawn correctly

Which direction does compatibility point?

writer schema

Debezium, at the moment it encodes a change event.

reader schema

Spark's normalizer, at the moment it decodes one.

ModeWhat it guarantees
BACKWARDa new reader can read old data
FORWARDan old reader can read new data
FULLboth directions hold
✓
We set cdc.public.orders-value to FULL.
the wire format

Five bytes before the data even starts.

BYTE 0 magic byte 0x00 BYTES 1–4 schema ID big-endian, 4-byte integer BYTES 5+ payload Avro-encoded record
ⓘ
The schema ID travels on every single message — a consumer never has to guess which schema wrote a record.
the trap

“Latest” is a lie for old records.

!
A retained topic holds records written under every schema version that has ever existed. Fetching the latest schema once and applying it to the whole batch silently corrupts the old records.
consumer — per-record schema ID
# the schema ID is inline on every record (bytes 1-4) — use it by_schema_id = defaultdict(list) for record in batch: schema_id = decode_schema_id(record.value) by_schema_id[schema_id].append(record) for schema_id, records in by_schema_id.items(): writer_schema = registry.get_schema(schema_id) normalized = [normalize(r, writer_schema, reader_schema) for r in records] union_batch.extend(normalized)

the container that's supposed to be dead

connector-init exiting is success.

Students always ask about this one. Answer it before they do.

docker compose ps
NAME STATUS … … connector-init Exited (0) ← this is the healthy final state
✓
connector-init is a one-shot job, not a service. It sends a single idempotent PUT to Kafka Connect that registers the Debezium connector config, then exits. It has nothing left to do, so it stops. Exited (0) means it succeeded — a nonzero code or a restart loop would be the actual failure signal.

hop ③ · kafka

An offset identifies an event, not an order.

FieldWhat it tells you
keythe order's primary key — routes it to a partition
valuethe Avro-encoded CDC envelope (before/after/source)
partitionone of 3 — cdc.public.orders has 3 partitions
offsetthis event's position within its partition only
schema IDthe Confluent registry ID encoded in the value's first 5 bytes
!
The offset orders nothing across partitions. With 3 partitions, two different orders' events can land on different partitions with no relationship between their offsets. Offset identifies an event within its own partition; it is not a global sequence number for current state.
hop ④ · spark

Checkpoint offsets are not consumer-group offsets.

Spark tracks its own read progress. Kafka's consumer-group API never sees it.

!
These offsets live in the Spark checkpoint, on a persistent volume — they are NOT Kafka consumer-group commits. That's the entire reason the dashboard metric is called offset-head distance and not consumer lag: a standard Kafka lag tool queries consumer-group offsets, and this pipeline never writes any.

Why the checkpoint has to be on a persistent volume, not /tmp: lose it, and Spark has no memory of what it already processed.

hop ⑤ · clickhouse

Raw rows vs. FINAL

without FINAL

clickhouse-client
SELECT * FROM lesson11.orders_current WHERE order_id = :id;

Can return several physical rows — one per version that hasn't merged yet.

with FINAL

clickhouse-client
SELECT * FROM lesson11.orders_current FINAL WHERE order_id = :id;

Merges versions at read time. One row: the highest version.

ⓘ
If that winning row is a delete marker, FINAL still returns it — it just merges duplicates, it doesn't know "delete" is special. The API is the layer that reads the marker and turns it into a 404.
hop ⑥ · api

The whole chain, one JSON body.

Source LSN, Kafka identity, sink-ingest timestamp — all in one response.

expand / contract

We only did the expand half.

  • What you just ran is expand: add, additive, backward-compatible, safe to run under live load.
  • Contract — removing the old field, forcing every consumer off it — is deliberately out of scope today.
!
Contract is where the outages live. Removing something means proving every consumer has already stopped depending on it — that's a coordination and rollback problem, not a schema-registry mechanism, and it's a real production migration, not a lesson demo.
the backpressure experiment

Inject a delay. Then hit it hard.

1 · inject a 10s sink delay SINK_DELAY_SECONDS=10 docker compose up -d --force-recreate stream-processor
2 · burst load uv run python scripts/load_generator.py --rate 200 --duration 60
3 · remove the delay, recover docker compose up -d --force-recreate stream-processor
ⓘ
SINK_DELAY_SECONDS is a lesson-only injection point — it does not exist in any production code path. It exists so you can manufacture backpressure on demand instead of waiting for it to happen.

Rough shape: two throughput lines that separate, a distance that climbs, a duration that crosses a flat 5s line, a freshness that ages — then all four reconverge once the delay is removed.

what you should actually see

Recovery needs drain rate > arrival rate.

  • arrival rises above processed throughput
  • offset-head distance grows
  • batch duration crosses the 5s trigger — the moment batches start queueing
  • freshness ages
!
Recovery requires drain rate > arrival rate — otherwise the backlog never catches up, no matter how long you wait.

Callback · Lesson 9: Spark's floor is max(trigger, batch_time) — you measured that yourselves. That's exactly why crossing the 5s trigger is the queueing threshold, not some other number.
