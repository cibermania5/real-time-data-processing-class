Fase 0 · la idea obvia

“Solo sincroniza lo que cambió.”

No releas un millón de filas cada noche, solo extrae las tocadas desde la última vez. Agrega una columna updated_at, recuerda una marca de agua alta y repite. Esto es CDC por sondeo, y es por donde empieza todo el mundo.

Fase 0 · el diagnóstico

Es la pregunta equivocada.

La desviación no son tres errores por parchar, es una pregunta imposible. “¿Qué cambió desde T?” es una pregunta que la tabla físicamente no puede responder con honestidad:

  • Los eliminados no dejan rastro. Una fila eliminada no está en ningún SELECT. Necesitarías borrados suaves en todas partes; ahora tu esquema OLTP se deforma por las necesidades de sincronización.
  • El orden de confirmación ≠ el orden de updated_at. Una transacción que empezó en T=100 pero se confirma en T=105 es invisible a un sondeo en T=103. La omites, o le agregas márgenes frágiles a la marca de agua alta.
  • Cada sondeo compite con producción. Sondea a menudo y cargas el servidor OLTP; sondea rara vez y tienes datos obsoletos. No hay un buen punto en ese dial.
Parchar cada síntoma solo mueve la mentira de lugar. La solución no es una mejor consulta, es una dirección diferente del flujo de información.

La inversión

Deja de preguntar. Suscríbete.

El sondeo es pull: interrogas la tabla con un temporizador. El CDC basado en registro es push: la base de datos te entrega un flujo continuo y ordenado de cada cambio confirmado, eliminaciones incluidas, exactamente una vez cada uno.

De dónde viene el flujo

Tienes el flujo desde la Lección 1.

¿Recuerdas el WAL? Cada transacción confirmada escribe sus cambios en el write-ahead log antes de que Postgres reconozca al cliente. Lo conocimos como mecanismo de durabilidad. También es otra cosa:

El WAL ya es un registro completo y ordenado de cada cambio en cada fila, un flujo de eventos escondido a plena vista.

El CDC no agrega un mecanismo nuevo a Postgres. Lee el que siempre estuvo ahí. La única pregunta es cómo elevar el WAL en bruto de vuelta a “la fila 42 pasó de pending a shipped”.
EL WALregistro de durabilidad = flujo de cambios
wal_level

Tres niveles. Solo uno decodifica.

wal_levelQué registraPara qué sirve
minimalSolo lo suficiente para recuperarse tras un falloNodo único, sin replicación

Un WAL a nivel replica dice “escribe estos bytes en esa página”, está por debajo del nivel de tablas y filas, así que no puedes reconstruir “status: pending→shipped” a partir de él. La decodificación lógica eleva el WAL de vuelta a tabla + operación + valores.

Fase 2 · el sink

Ya construiste la lógica de aplicación.

Mapea cada evento en DuckDB. Para actualizaciones, usa DELETE + INSERT, la jugada idempotente exacta de la Lección 4. Aplica el mismo evento dos veces y la fila es idéntica.

cdc_consumer.py, DuckDBSink
def apply(self, ev): if ev["action"] in ("I", "U", "D"): duck.execute("DELETE FROM orders WHERE id = ?", [ev.id]) if ev["action"] in ("I", "U"): duck.execute("INSERT INTO orders VALUES (?, ?, ?, ?, ?)", ev.row) # delete runs for I too: a replayed INSERT is a no-op, not a dup key.
¿Por qué no un simple UPDATE ... SET? Porque cualquier consumidor de CDC puede caerse y reproducir eventos. Aplicar de forma idempotente significa que reproducir es inofensivo, la propiedad que te deja dormir, de nuevo.
EL SINKdelete+insert = idempotente
Fase 3 · el bucle principal

La marca de agua, entregada a ti.

En la Lección 4 calculaste una marca de agua para saber qué ya estaba cargado. Aquí Postgres la guarda por ti: confirmed_flush_lsn. El bucle es de tres verbos: echar un vistazo a los cambios pendientes (no avanza nada), aplicarlos y solo entonces avanzar el slot.

cdc_consumer.py, the loop
rows = pg.execute("SELECT lsn, data FROM pg_logical_slot_peek_changes( 'orders_slot', NULL, 5000, ...)") # 1. peek — advances nothing for lsn, data in rows: sink.apply(json.loads(data), lsn) # 2. write it pg.execute("SELECT pg_replication_slot_advance( 'orders_slot', %s)", [last_commit_lsn]) # 3. THEN confirm
Avanzar le dice a Postgres “recicla el WAL hasta aquí”. Avanzar antes de aplicar y un fallo pierde el cambio; nunca avanzar y el slot retiene el WAL para siempre. Y avanza solo hasta el LSN de un marcador de confirmación, las posiciones a mitad de transacción no son puntos seguros. Regla: aplica, luego confirma. Kafka te hace jugar exactamente este juego otra vez; allí se llama confirmar tu offset (Lección 6).

Caso 01 · el millón perdido

El slot solo ve el futuro.

Tu consumidor es perfecto, pero DuckDB tiene 4 filas nuevas y Postgres tiene 1.000.004. El slot empezó en su consistent_point; el millón de filas que existían antes de él nunca fluyeron.

the gap
postgres orders 1,000,004 duckdb orders 4 ← only post-slot changes
Un flujo de cambios no es una copia. Para construir un espejo completo necesitas una instantánea única de lo que ya estaba ahí, cosida al flujo sin hueco ni superposición.
BRECHA DE INSTANTÁNEAflujo ≠ copia
Caso 01 · la solución

Instantánea del pasado. La reproducción sella la costura.

Crea el slot primero, así el flujo ya está almacenando todo lo que ocurra después. Luego copia masivamente la tabla, un SELECT, una instantánea MVCC. La costura: algunos cambios caen tanto en la copia como en el flujo. No peleamos contra eso, el sink idempotente los reproduce como una no-op.

snapshot.py
# 1. slot already exists → every change since is buffered for replay duck.execute("ATTACH 'postgres://...' AS pg (TYPE postgres)") duck.execute("INSERT INTO orders SELECT ... FROM pg.orders") # the past # 2. drain the slot: overlapping events re-apply as delete+insert → no-op $ uv run python src/cdc_consumer.py # the future
La fase de “instantánea inicial” de Debezium consigue una costura exacta sin superposición exportando la instantánea del slot a través del protocolo de replicación. Cambiamos esa ceremonia por SQL sencillo más idempotencia, y convergemos al mismo espejo. De cualquier forma, la instantánea puede durar horas en una tabla grande; ahora sabes qué está haciendo y por qué.

Aparece una columna a mitad del flujo.

Arriba ejecutan ALTER TABLE orders ADD COLUMN notes TEXT. El flujo no se rompe, wal2json simplemente empieza a emitir el campo nuevo. Tu consumidor tiene que notarlo y reaccionar.

  • Detecta la clave no vista en el payload del evento, compárala con las columnas que DuckDB conoce.

Caso 04 · en vivo

Un slot olvidado es una bomba de tiempo.

Crea un slot, nunca lo consumas, corre el generador. Postgres no puede reciclar el WAL que el slot no haya confirmado, así que se acumula hasta que el disco se llena y las escrituras se detienen.

$ uv run python src/experiment_abandon_slot.py
slot 'abandoned_slot' created, nothing is reading it retained_wal 120 MB ... 480 MB ... 2.1 GB postgres: FATAL: could not write to WAL, no space left fix -> SELECT pg_drop_replication_slot('abandoned_slot');
Un slot no monitoreado puede tumbar la base de datos origen. max_slot_wal_keep_size (PG 13+) es la válvula de seguridad: suelta un slot codicioso para salvar la BD, a costa de una re-instantánea forzada.
DISK-FULLslot retains WAL → outage
Ruptura · la regla única

Cada slot necesita un consumidor monitoreado.

Un slot de replicación es una promesa de que el origen conserva el WAL para ti. Rompe la promesa, abandonando o estancando el consumidor, y el origen paga con disco. Así que el contrato operativo es corto:

  • Alerta cuando confirmed_flush_lsn se quede atrás de pg_current_wal_lsn().
  • Configura max_slot_wal_keep_size para que un consumidor atascado nunca hunda la base de datos.
  • Mantén la ruta de aplicación idempotente, así la reproducción inevitable es una no-op.

Mirando adelante · el outbox

Un truco más que desbloquea el CDC.

Una trampa clásica de sistemas distribuidos: una app debe escribir en la BD y publicar un evento. Hazlos por separado y uno puede tener éxito mientras el otro falla. El patrón outbox lo disuelve.

one local transaction, no 2PC
BEGIN; INSERT INTO orders (...) VALUES (...); INSERT INTO outbox (event_type, payload) VALUES (...); COMMIT; # CDC streams the outbox row downstream, exactly-once
Un problema de consistencia distribuida se convierte en una transacción local más una lectura CDC. Esta es la columna vertebral de las Lecciones 6–7, una vez que Kafka sea quien lea el flujo.

Anexo

Lee antes de depurar.

  • wal2json debe estar presente. postgres:16 vanilla solo trae pgoutput + test_decoding; nuestra imagen incluye wal2json. Cambia a test_decoding si no puedes instalarlo.
  • wal_level=logical necesita un reinicio y aumentar max_replication_slots / max_wal_senders. Ya está configurado en Compose.
  • Un slot, un lector. Dos consumidores en el mismo slot pelearán; dale a cada uno su propio slot (y duplica el costo de WAL, la motivación de L6).
  • Dos formas de leer un slot. SQL sencillo, peek_changes + slot_advance, es lo que usamos. El protocolo de replicación por flujo (replication=True, send_feedback) es lo que usa Debezium, el mismo contrato de confirmar-después-de-aplicar, más tubería.
  • Suelta los slots que dejes de usar. Un slot ocioso sigue reteniendo WAL hasta que llena el disco.
