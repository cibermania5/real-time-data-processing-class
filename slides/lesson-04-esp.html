Resumen · lección 3

Dos mundos. Una brecha.

OLTP, donde nacen los datos
  • Postgres, almacén de filas: inserta un pedido rápido
  • Búsquedas puntuales en B-tree, transacciones, restricciones
  • Pésimo para “escanear 10M de filas y agregar”
OLAP, donde se responden las preguntas
  • DuckDB, almacén de columnas: escanea + agrega rápido
  • Vectorizado, comprimido, 10×+ en analítica
  • Pésimo para inserciones y búsquedas por fila
Tus datos nacen en OLTP, pero la analítica los necesita en OLAP. Algo tiene que moverlos a través de la brecha, de forma fiable, cada día. Ese algo es un pipeline de datos, hoy el clásico tipo por lotes.

Vocabulario

¿Dónde ocurre la T?

  • ETL: extraer → transformar → cargar. La forma que dibujan todos los libros de texto.
  • ELT: extraer → cargar → transformar. La forma que la era del almacén en la nube hizo barata.
Nuestro pipeline es híbrido. Extraemos con psycopg, luego transformamos y cargamos dentro de DuckDB: rendimiento tipo ELT a partir de una forma técnicamente ETL. La etiqueta importa menos que los cuatro problemas, que son universales.

ETL vs ELT · una breve historia

Cargar primero llegó primero.

El orden sigue cambiando con el costo del cómputo y el almacenamiento. Tres eras, y la razón por la que ganó cada una:

EraFormaCómo funcionóPor qué ganó
1990sELT (antes del término)Cargar archivos planos a staging, transformar en el almacénLa única opción; staging era caro, se borraba después de usarlo
2000sETLUn servidor de integración (Informatica, etc.) transforma en memoria antes de cargarEliminó la contención de staging; arrastrar y soltar visual sobre SQL
2010s+ELTAlmacenamiento en la nube barato; transformar en el almacén con dbt (SQL + Jinja)Separación de cómputo y almacenamiento, clústeres separados, los datos en bruto se quedan
Contraintuitivo, pero real: cargar y luego transformar es anterior a las herramientas ETL dedicadas que la mayoría asume que llegaron primero. La nube no inventó ELT, lo hizo barato de nuevo. El péndulo sigue una sola cosa: dónde es más barato ejecutar el cómputo.

Extraer y transformar

Extrae un día. Agrega.

La forma obvia: leer un día de pedidos desde Postgres, entregar las filas a DuckDB, dejar que haga el GROUP BY. Aburrida a propósito, cada paso permanece visible.

pipeline_naive.py, extract() + transform()
# EXTRACT: one day, explicit columns (never SELECT *) rows = pg.execute("SELECT id, customer_id, amount, status, created_at " "FROM orders WHERE created_at::date = %s", [day]) # TRANSFORM: push the GROUP BY into DuckDB agg = duck.execute("SELECT ?::DATE, status, SUM(amount), COUNT(*), " "ROUND(AVG(amount),2) FROM raw GROUP BY status", [day])
Tiramos del día a Python para que cada etapa sea legible. Los frameworks (más adelante) preparan a través de Parquet, las mismas tres etapas. Lo único que se mantiene sin cambios es la carga. Ahí es donde viven los cuatro problemas.

IdempotenteUna operación que puedes aplicar muchas veces obteniendo el mismo resultado que si la aplicaras una vez. f(f(x)) = f(x).
Problema 01 · Idempotencia

Ejecútalo tres veces.
Mismo estado.

El planificador sí reejecutará tu trabajo: reintentos, backfills, un ingeniero nervioso presionando el botón. La carga ingenua inserta a ciegas: tres ejecuciones, triple de filas, y un número de ingresos que miente en silencio.

IDEMPOTENCIAmismas entradas → mismo estado
Reemplazo de particiónBorra el slice que vas a reescribir, luego insértalo de nuevo. Re-ejecutar simplemente reescribe el mismo slice.
Corrección 01a

Estrategia 1, DELETE + INSERT

pipeline_idempotent.py
con.execute("BEGIN TRANSACTION") try: con.execute("DELETE FROM daily_revenue WHERE date = ?", [day]) for r in rows: con.execute("INSERT INTO daily_revenue VALUES (?,?,?,?,?,?)", r) con.execute("COMMIT") # both steps land together… except Exception: con.execute("ROLLBACK"); raise # …or neither does
Funciona sin clave primaria. Define la “partición” (aquí, una date) y reemplázala por completo. La opción predeterminada más robusta.
CARGA IDEMPOTENTEeliminar-insertar
UPSERTInsertar, pero en una colisión de claves sobrescribir la fila existente. Una sentencia, sin eliminación explícita.
Corrección 01b

Estrategia 2, UPSERT

pipeline_idempotent.py, load_upsert
con.execute(""" INSERT OR REPLACE INTO daily_revenue_keyed (date, status, total_revenue, order_count, avg_order_value, loaded_at) VALUES (?, ?, ?, ?, ?, ?) """, row) # re-inserting the same key overwrites in place
$ uv run src/pipeline_idempotent.py 2024-01-15 --strategy upsert
UPSERT necesita una clave. Apunta a daily_revenue_keyed, que declara PRIMARY KEY (date, status), el objetivo del conflicto. Sin clave, no hay “reemplazo”.
UPSERT solo toca las claves que reaparecen. Si un estado desaparece de los datos de un día, su fila obsoleta sobrevive, una clave huérfana. DELETE + INSERT reescribe toda la partición, así que también limpia las claves desaparecidas. Por eso es la opción más segura por defecto; experiment_upsert_gap.py demuestra la diferencia.
CARGA IDEMPOTENTEinsertar-o-reemplazar · claves huérfanas
Problema 01 · en vivo

La carga ingenua crece.

La carga es un bucle INSERT a ciegas, sin DELETE, sin clave. Ejecuta el mismo día tres veces y observa el harness de pruebas:

$ uv run python src/prove_idempotent.py --loader naive
run rows checksum 1 3 b04a42b3c882 2 6 da58b0d4b47f 3 9 593f71c60c10 NOT IDEMPOTENT: 3 distinct states across 3 runs.
Cada reintento agrega otro día completo. El checksum cambia porque los ingresos se triplican, un número que miente en silencio.
CARGA INGENUAINSERT a ciegas → duplicados
Corrección 01 · en vivo

Mismas entradas. Mismo estado.

Cambia el INSERT a ciegas por el DELETE + INSERT en una transacción. Vuelve a ejecutar el mismo día tres veces:

$ uv run python src/prove_idempotent.py 2024-01-15
run rows checksum 1 3 b04a42b3c882 2 3 b04a42b3c882 3 3 b04a42b3c882 IDEMPOTENT: all 3 runs produced identical state (3 rows).
Checksum idéntico, en cada ejecución. El DELETE convierte la re-ejecución en una no-op, la partición se reemplaza con los mismos bytes. Este es el estándar entregable: prove_idempotent.py.
CARGA IDEMPOTENTEchecksum idéntico ×3
Problema 02 · Recuperación

El truco es la transacción.

DELETE y luego INSERT parecen seguros, hasta que se bloquea después del delete. Sin una transacción, acabas de vaciar los ingresos de ayer y no escribiste nada de vuelta. Ese es el fallo de bloqueo a mitad de carga, y la transacción es cómo te recuperas de él.

DELETE, cada INSERT y (más adelante) la escritura del watermark comparten una transacción. O se confirma todo el nuevo estado, o el antiguo sobrevive intacto. Eso es lo que hace segura una re-ejecución.
ATOMICIDADtodo-o-nada
Problema 02 · en vivo

Bloqueo a mitad de carga. Reintenta. Sin corrupción.

Inyecta un fallo aleatorio dentro del bucle INSERT, envuelve la carga en un reintento. Como la carga es idempotente, reintentar es seguro, no una máquina de duplicación.

$ uv run python src/pipeline_failure.py --fail-prob 0.4
Attempt 1/8 FAILURE: crash after 1 of 3 rows, rolled back, target unchanged Attempt 2/8 FAILURE: crash after 2 of 3 rows, rolled back, target unchanged Attempt 3/8 Success on attempt 3 (3 rows)
Dos bloqueos, cero corrupción. Cada intento fallido hace ROLLBACK del DELETE también; el destino es byte a byte su yo antiguo hasta un COMMIT limpio. Los reintentos sin idempotencia simplemente duplican más rápido.
RECUPERACIÓN DE FALLASrollback + reintento
Marca de aguaUn registro duradero de qué particiones terminaron. Una re-ejecución las salta; un backfill llena los huecos. (No es la marca de agua de event-time del streaming: misma palabra, idea distinta. Esa está en L5.)
Problema 02 · Recuperación, a escala de rangos

Carga un rango. Salta lo que ya está.

La recuperación escala de una fecha a un rango completo: un libro mayor pipeline_metadata registra cada fecha terminada, así que un bloqueo a mitad de un backfill simplemente reanuda. Ejecuta el mismo rango dos veces:

corrida 1 · 01-10 .. 01-20
2024-01-10 loaded 3 (11,112) 2024-01-11 loaded 3 (11,032) … … 2024-01-20 loaded 3 (11,239)
corrida 2 · mismo rango
2024-01-10 skip (watermark) 2024-01-11 skip (watermark) … … 2024-01-20 skip (watermark)
11 fechas cargadas, luego 11 saltadas. --force reprocesa de todos modos, y eso es seguro, porque la carga subyacente es idempotente.
MARCA DE AGUAcargar una vez · saltar · llenar huecos del backfill
La sutileza que muerde

“Cargado” y “registrado como cargado” son un hecho.

pipeline_watermark.py, load_and_mark()
con.execute("BEGIN TRANSACTION") con.execute("DELETE FROM daily_revenue WHERE date = ?", [day]) # ... INSERT the day's rows ... con.execute("INSERT OR REPLACE INTO pipeline_metadata ...") # the mark con.execute("COMMIT") # data + watermark land together, or not at all
Marcar después de un commit separado → bloqueo en medio → la fecha parece no cargada, se recarga en silencio. Marcar antes de que los datos se confirmen → la fecha parece hecha pero no tiene datos. Ambos son corrupción silenciosa. Una transacción borra la brecha, exactamente lo que hace la base de datos de metadatos de un orquestador por ti.

Problema 03 · Dimensiones de cambio lento

La dimensión que no se queda quieta.

Los hechos son inmutables: un pedido ocurrió, por $42, el día 15. Pero el cliente detrás cambia: se muda de Chicago a LA.

  • Sobrescribirlo, y cada pedido pasado de repente parece venir de LA. Historia reescrita.
  • Ignorarlo, y los pedidos nuevos se etiquetan con una ciudad obsoleta. Presente equivocado.
  • Necesitas responder “¿dónde vivía este cliente cuando ocurrió el pedido?”

Problema 04 · Desviación del esquema

Arriba cambia la forma.

No eres dueño de la fuente. Algún día un desarrollador de backend renombra una columna, y tu pipeline o falla, o peor, sigue ejecutándose con datos erróneos.

Cambio arribaQué te haceSeveridad
Agregar una columnaNada, si nunca usas SELECT *Seguro
Eliminar / renombrar una columnaLectura de una columna ausente, fallo duroRuidoso
Cambiar el tipo de una columnaConversión / truncamiento silencioso, datos corruptosPeligroso
Reordenar columnasSELECT * desalinea cada valorPeligroso
Misma forma, nuevos valoresLa verificación del esquema pasa; los agregados están silenciosamente malEl peor
Los peligrosos son silenciosos. Un fallo ruidoso te despierta; uno silencioso envía números erróneos durante un mes. El peor no toca el esquema en absoluto: un status crece un nuevo valor, un amount se vuelve negativo. Por eso solo verificar la forma no es suficiente.
EVOLUCIÓN DEL ESQUEMAagregar · eliminar · cambiar tipo · reordenar
Corrección 04

Haz que la desviación sea ruidosa. A propósito.

  • Nunca uses SELECT *. Lista cada columna por nombre; el reordenamiento y las columnas sorpresa no pueden hacerte daño.
  • Fija un contrato. Declara las columnas + tipos que esperas; verifica la fuente en vivo contra él antes de cargar.
  • Fallar rápido. Columna ausente/cambiada de tipo → detener con un error claro. Nueva columna → advertir, continuar.
  • Luego verifica valores, no solo forma. El contrato atrapa una columna renombrada; no atrapará un amount negativo o un status desconocido. Asegura los invariantes que tus agregados asumen: eso es data_quality.py.
schema_validate.py
for col, want_type in CONTRACT.items(): if col not in live: fail(f"missing column '{col}' (renamed or dropped upstream)") elif live[col] != want_type: fail(f"type drift on '{col}': {live[col]} != {want_type}")

CONSTRUIDO A MANO · LISTOscript correcto ≠ pipeline
De script a sistema

Un script correcto no es un pipeline.

Digamos que cada problema de arriba está resuelto. Todavía tienes un archivo .py. Ahora ejecútalo durante 365 días, en el orden correcto, con reintentos y sabiendo cuándo se rompe.

  • Programación: ejecutar a las 02:00 todos los días, no un cron en la laptop de alguien
  • Dependencias: cargar solo después de que extraer y transformar tengan éxito
  • Reintentos + alertas: intentar de nuevo, luego avisar a un humano
  • Backfill: volver a ejecutar ene 1–90 limpiamente (¡necesita idempotencia!)
  • Observabilidad: qué se ejecutó, cuándo, cuánto tiempo, por qué falló
  • Linaje: qué entradas produjeron qué salidas
Ese conjunto de preocupaciones tiene un nombre: un orquestador. Veremos dos, Airflow y Dagster, a continuación.
ORQUESTACIÓNprogramar · depender · reintentar · backfill · observar
La parte que todos entienden mal

Lo que un orquestador no hará.

Te da
  • Programación y triggers
  • Dependencias de tareas (el DAG)
  • Reintentos, alertas, backfill
  • Una UI, logs, linaje
No te da
  • Idempotencia
  • Corrección en re-ejecución
  • Cargas transaccionales
  • Seguridad de esquema
Los reintentos son una trampa sin idempotencia. Un planificador que re-ejecuta un trabajo no idempotente simplemente duplica tus datos más rápido. Las cuatro correcciones que acabas de construir a mano son el prerrequisito, no la reflexión posterior.

Anexo · trucos

Lee antes de depurar.

  • DuckDB es de escritor único. Runner, Airflow y Dagster comparten un archivo, ejecutan un escritor a la vez (por eso max_active_runs=1).
  • Airflow catchup=False a propósito, así que no hará backfill de dos años en una laptop. Usa airflow backfill create --from-date --to-date para un rango acotado.
  • Niveles de reset: elimina data/analytics.duckdb para borrar el destino; docker compose down -v también borra los datos iniciales + los metadatos de Airflow.
  • La zona horaria muerde el filtro de fecha. created_at::date usa la zona de la sesión, así que el conteo de filas de un día cambia bajo UTC vs local. experiment_timezone.py lo muestra; fija una zona para backfills reproducibles.
  • El primer docker compose up -d es lento, construye las imágenes y descarga Postgres ×2.
El mismo Postgres, wal_level=logical ya activado, así que la demo de CDC de la Lección 5 se ejecuta contra esta fuente exacta, sin reaprovisionar.

Anexo · scripts (1/2)

Infraestructura y fases del pipeline.

config.py: Configuración de conexión compartida y del esquema. Define el DSN de Postgres, la ruta de DuckDB, crea las tablas destino. Todos los scripts importan de aquí.
seed_data.py: Genera ~1M de pedidos y ~50k clientes en Postgres usando la extensión postgres de DuckDB para COPY rápido del lado del servidor. Cantidad de pedidos, cantidad de clientes y ventana de fechas configurables.
probe_data.py: Muestra el estado actual de ambas bases de datos: conteos de filas, rangos de fechas, datos de muestra. Usa --reset para borrar DuckDB y volver a sembrar Postgres.
pipeline_naive.py: Fase 1: extraer → transformar → carga por apéndice ciego. Sin idempotencia, las re-ejecuciones duplican filas. Muestra el problema.
pipeline_idempotent.py: Fase 2: agrega idempotencia mediante DELETE+INSERT o UPSERT. Las re-ejecuciones producen el mismo estado.
pipeline_failure.py: Fase 3: inyecta fallos aleatorios a mitad de carga para demostrar recuperación transaccional. DELETE+INSERT en una transacción significa que ROLLBACK deja el destino sin cambios.
pipeline_watermark.py: Fase 4: pipeline multi-fecha con un libro mayor pipeline_metadata para rastrear fechas cargadas. Lección crítica: la escritura de datos y la escritura de metadatos deben confirmarse en la MISMA transacción.

Anexo · scripts (2/2)

Pruebas, validación y casos límite.

prove_idempotent.py: Ejecuta un pipeline N veces y compara conteos de filas + checksums. Comprueba idempotencia (todas las ejecuciones idénticas) o detecta duplicación (loader ingenuo).
scd2.py: Merge SCD Tipo 2 para la dimensión customer. Detecta clientes cambiados, expira versiones antiguas, inserta nuevas con ventanas valid_from/valid_to. Incluye --simulate-move para mutar la fuente y --show para ver el historial de versiones.
schema_validate.py: Declara el esquema fuente esperado (nombres de columnas + tipos). Consulta information_schema.columns y compara contra el contrato. Detecta columnas ausentes, cambios de tipo y nuevas columnas.
data_quality.py: Verificaciones de calidad de datos a nivel de valores en fuente y destino (montos negativos, nulos, desajustes de ingresos). Atrapa problemas que el contrato de esquema no alcanza.
experiment_upsert_gap.py: Demuestra el problema de claves huérfanas de UPSERT: si una clave desaparece de la fuente, UPSERT deja la fila antigua atrás mientras DELETE+INSERT la elimina.
experiment_timezone.py: Muestra cómo los límites de partición de created_at::date cambian según la zona horaria de la sesión. Cuenta filas para una fecha en UTC, America/Los_Angeles y Asia/Tokio.
Todos los scripts aceptan --help. Las fases del pipeline se construyen unas sobre otras: ingenuo → idempotente → fallo → watermark. Ejecútalos en orden para ver cómo se acumulan las correcciones.
